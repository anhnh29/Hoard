## Project

Hoard is a Medium-style publishing platform, in early MVP development. See [docs/architecture.md](docs/architecture.md) for the full architecture/tech-stack decisions, [docs/features.md](docs/features.md) for the feature brief, and `plans/` for the phase-by-phase implementation plans.

It is a pnpm + Turborepo monorepo with two apps:

- `apps/web` — Nuxt 4 (SSR), the frontend.
- `apps/api` — NestJS, the backend, connected to PostgreSQL via Prisma.

And one shared package:

- `packages/shared` — TypeScript types shared between `apps/web` and `apps/api` (e.g. `HealthStatus`), built with `tsc` to `dist/` and consumed like any workspace dependency.

As of Phase 0 (setup), there is no domain/feature code yet — only the plumbing proving `apps/web` -> `apps/api` -> PostgreSQL works end to end via a `/health` endpoint.

## Commands

This project uses **pnpm** (declared via `packageManager` in package.json) with **Turborepo** orchestrating tasks across packages.

- `pnpm install` — install dependencies for every package in the workspace
- `pnpm dev` — run `apps/web` and `apps/api` together (via `turbo run dev`); `apps/web`'s dev task depends on `packages/shared` being built first
- `pnpm build` — build all packages (`turbo run build`)
- `pnpm test` — run all packages' test suites (`turbo run test`)

Per-package commands (use pnpm's `--filter`):
- `pnpm --filter @hoard/api start:dev` — run only the NestJS API in watch mode
- `pnpm --filter @hoard/api test` / `test:e2e` — Jest unit / e2e tests for the API
- `pnpm --filter @hoard/web dev` — run only the Nuxt web app
- `pnpm --filter @hoard/web test` — Vitest tests for the web app
- `pnpm --filter @hoard/shared build` — rebuild the shared package's `dist/` (needed if you change `packages/shared/src` and aren't going through `turbo`)

**Local database:** `apps/api` needs Postgres. Start it with `docker compose up -d db` (repo root) — maps to host port **5434**, not 5432, because 5432 is commonly already taken by a local Postgres install. `apps/api/.env` (gitignored; copy from `apps/api/.env.example`) points `DATABASE_URL` at port 5434.

There is no linter configured yet across the monorepo. If you add one, record the command here.

## Architecture

- **Workspace layout:** `pnpm-workspace.yaml` declares `apps/*` and `packages/*`. `turbo.json` defines the `build`/`dev`/`test` task pipeline — `build` and `test` depend on `^build` (a package's dependencies build first); `dev` also depends on `^build` so that `packages/shared`'s compiled output exists before `apps/api`/`apps/web` start.
- **apps/web** uses Nuxt 4's `app/` directory convention (srcDir defaults to `app/`) — put pages/components/composables under `app/` (e.g. `app/pages/`, `app/composables/`), following standard Nuxt auto-import/auto-routing. `nuxt.config.ts` exposes `runtimeConfig.public.apiBase` (overridable via `NUXT_PUBLIC_API_BASE`) as the base URL for calling `apps/api`.
- **apps/api** is a standard NestJS module/controller/service app generated by the Nest CLI. `PrismaService` (`src/prisma/prisma.service.ts`) wraps `PrismaClient` with Nest's `OnModuleInit`/`OnModuleDestroy` lifecycle and is injected wherever a module needs the database.
- **packages/shared** has no build-on-install step of its own — it relies on Turborepo's `^build` dependency to be compiled before a consumer needs it. If you ever run a consumer outside of `turbo` (e.g. `pnpm --filter @hoard/api start:dev` right after a fresh clone), build `packages/shared` first.
- **Prisma schema** (`apps/api/prisma/schema.prisma`) has no models yet as of Phase 0 — domain models (`User`, `Article`, etc.) are added starting Phase 1, per `plans/phase-1-auth-profile.md` onward. `prisma`/`@prisma/client` are pinned to an exact version (not a caret range) because Prisma 7 dropped support for the `datasource.url` syntax this schema uses.
